Tooling caveatEdit-lens wheel-scroll could not be conclusively tested

The canvas content lives inside iframe.preview-frame. Automated wheel-scroll events dispatched at this iframe never moved scrollTop, while the identical scrollbar dragged by mouse-down/move/up worked immediately, and the exact same page loaded standalone (outside the iframe) scrolled normally on wheel input. Code-lens, which is native DOM rather than an iframe, also scrolled correctly on wheel input. No wheel listener exists anywhere in the editor's JS. This isolates the gap to synthetic-wheel-over-cross-frame event delivery in the automation layer, not the product — but it could not be ruled out with a real trackpad in this session.

ModerateNavigate away with dirty state — silently discarded, zero warning

Typed an edit, did not save, clicked "Back to WordPress." No beforeunload handler exists anywhere in the editor (confirmed: window.onbeforeunload is not a function, and a dispatched beforeunload event was never defaultPrevented). The click reset the editor and the unsaved text vanished with no prompt. The original content was untouched — this is data loss, not corruption — but it directly misses the spec's own bar: "warn or lose-intentionally, never silently corrupt." A user has no way to know their edit didn't save.

ModerateInvalid Schema (JSON-LD) save fails with zero user-visible feedback

Typed {not valid json,,, into Page Settings → Schema, clicked "Save schema." No error, no toast, no red border appeared. Server-side confirmed correct — _s5_schema_json postmeta was never written — so the rejection itself works. But the user is left staring at a form that appears to have done nothing, with no way to know their input was silently thrown away.

05Viewports + WebKit

Editor viewport toggle (in-app simulation) is confirmed working — see Section 01. Real device-width emulation for the served-page screenshot matrix could not be forced in this session; a code-level check surfaced a severe, independently-confirmed finding instead.

SevereThe compiled design system has zero responsive CSS

Grepped the shipped bundle and all four source stylesheets for any responsive mechanism. All four return zero matches:

$ grep -c "@media" site/dist/s5.css 0 $ grep -c "@media" site/styles/{tokens,utilities,components,scales}.css tokens.css:0 utilities.css:0 components.css:0 scales.css:0 $ grep -c "clamp(\|container-type\|@container" site/dist/s5.css 0

No @media queries, no container queries, no fluid clamp() typography — nothing. Every served page renders the identical fixed-width desktop layout at every viewport width; a phone visitor gets the desktop grid scaled into a narrow window, not a responsive redesign. This is the compiled bundle actually shipped in the tagged zip (448 lines, real content — not a truncated build), so this is not a build artifact.

Not verified375 / 768 / 1440 screenshot matrix + WebKit pass

The available browser-resize tool changed the outer Chrome window (outerWidth) but not the page's actual rendering viewport (window.innerWidth stayed 1442 regardless of the requested size) — confirmed via direct JS inspection, so a screenshot taken under it would not have reflected a real mobile viewport and is not included. No WebKit/Safari-engine browser context was available in this session to run the parity pass. Given the finding above, a true viewport test would very likely show the same fixed-width layout at every breakpoint — but that specific claim is unverified pending a session with real device emulation.

06Roles as real users

Three real WordPress users created, one per documented tier, logged in as each: qa_client (Author), qa_marketer (Editor), qa_developer (Administrator). Cleaned up after testing.

SevereRoles & Access is fully built, fully documented, and non-functional for 2 of its 3 tiers

The Roles settings screen explicitly documents:

  • Client (→ WP Author): "In the canvas, sees only the Content and Style tabs — no Advanced, no structure surgery."
  • Marketer (→ WP Editor): "Can open Theme Settings, but not Roles, CSS/Tailwind, or Deploy."

Both claims are false in the shipped code. Editor::CAPABILITY and Settings::CAPABILITY are both hard-coded to manage_options — Administrator-only — checked before the granular Roles::can() permission matrix ever runs. Neither Author nor Editor holds manage_options by default, so both roles are blocked outright, server-side, from the editor and Theme Settings — not tab-restricted as documented, but fully locked out.

# logged in as qa_client (Author) GET /wp-admin/admin.php?page=s5-editor&post=5 → "Sorry, you are not allowed to access this page." GET /wp-admin/admin.php?page=s5-settings → "Sorry, you are not allowed to access this page." # logged in as qa_marketer (Editor) GET /wp-admin/admin.php?page=s5-settings → "Sorry, you are not allowed to access this page." # source s5-theme/src/Editor.php:46: CAPABILITY = 'manage_options'; s5-theme/src/Settings.php:40: CAPABILITY = 'manage_options'; s5-theme/src/Settings.php:37: // gate is manage_options (Developer/Administrator) with per-screen role checks

The comment at Settings.php:37 confirms this was a known, intentional simplification — never finished. The permission matrix on the Roles screen (a real, separately-built Roles::can() layer) is fully implemented and presumably correct, but structurally unreachable for anyone but an Administrator. This is the single most consequential finding in this sweep: an entire, prominently-documented settings feature does nothing for the two roles it exists to support.

PassClient sidebar correctly minimal

Logged in as qa_client, the wp-admin sidebar shows only Dashboard, Posts, Media, Comments, Profile, Tools — no Pages, no Appearance, no S5. Matches "never sees this settings page at all" for the settings link itself, even though the underlying block is the wrong mechanism (see above).

PassBlocks are real server-side blocks, not just hidden UI

Every blocked URL returned WordPress's native "Sorry, you are not allowed to access this page" — a wp_die()-level capability check, not a client-side route guard. Hidden and blocked, exactly as the sweep required — just blocking the wrong set of roles.

08Docs truth test

README.md and DEMO.md read literally against the current, real state of the repo.

SevereREADME.md describes an architecture that no longer exists

README.md states the project is at "Build Order Step 6 complete," describes s5-plugin/ as "the shippable unit" holding its own composer.json/vendor/, and lists the editor, Components, and MCP under "Not built yet." None of this is true today:

  • The gate this session ran (and every suite this sweep exercised) covers Steps 0–12, plus Item 2, Distribution, and Phase A/B/C — many steps past what README.md claims.
  • s5-plugin/ does not exist on disk at all — confirmed by direct listing. DEMO.md correctly says the opposite: "the framework ships as a single theme — there is no companion plugin."
  • The editor and Components settings screen are fully built and are exactly what this entire sweep has been testing.

A developer or agent following README.md's setup instructions (composer install -d s5-plugin) would fail on the first command against a fresh clone. This is not a stale detail — it is a structurally incorrect map of the codebase, left over from before the single-theme repackage. Rewriting it is a substantial task in its own right and out of scope for a fix-forward pass inside this sweep; flagging it here as the sweep's top documentation finding.

ModerateDEMO.md's "deliberately left out" list contradicts a shipped feature

DEMO.md line 177 lists "Capability-levels UI" under features this cut deliberately leaves out. The product now ships a fully-built Roles & Access settings screen with a permission matrix — see Section 06. Either this line is stale (the feature landed after the doc was last touched) or the feature was shipped in a half-finished state and the doc line was never revisited either way. Worth reconciling alongside the Section 06 fix.

PassDEMO.md's Setup & Status claim, verified true

DEMO.md promises an "N existing pages found — rendering via the styled fallback until adopted" list on Setup & Status. Confirmed live: "1 existing page found," listing Sample Page with a working "Adopt into S5" action.

Not verifiedFull literal DEMO.md walkthrough, step-by-step, on a truly fresh install
